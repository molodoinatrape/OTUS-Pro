## 1. Модульные тесты

Разработать **unit-тесты основного функционала** API. Разрешается использовать любой тестовый фреймворк: `unittest`, `nosetests`, `pytest` и другие.

## 2. Разные наборы данных для одного теста

Обязательно реализовать через декоратор запуск одного теста с разными **тест-векторами** - наборами входных данных. Альтернатива из условия - параметризация через фикстуры pytest.

Если используется готовый `cases`, доработать его так, чтобы при падении было понятно, **какой именно сценарий упал**.

Пример из условия:

```python
@cases([
    {
        "account": "horns&hoofs",
        "login": "h&f",
        "method": "online_score",
        "token": "",
        "arguments": {},
    },
    {
        "account": "horns&hoofs",
        "login": "h&f",
        "method": "online_score",
        "token": "sdd",
        "arguments": {},
    },
    {
        "account": "horns&hoofs",
        "login": "admin",
        "method": "online_score",
        "token": "",
        "arguments": {},
    },
])
def test_bad_auth(self, request):
    ...
```

## 3. Хранилище в store.py

Ранее вместо хранилища передавалось `None`. Теперь реализовать в `store.py` общение с **клиент-серверным key-value хранилищем** по интерфейсу обновлённого [scoring.py](../../../docs&practice/08-09%20-%20Тестирование/08%20-%20Pytest%20и%20как%20писать%20тесты/scoring.py).

Можно выбрать Tarantool, Memcached, Redis или другое подходящее хранилище.

### Интерфейс, используемый в шаблоне

| Метод | Назначение |
| --- | --- |
| `cache_get(key)` | Получить оценку из кеша |
| `cache_set(key, value, ttl)` | Сохранить оценку в кеше на заданное время |
| `get(key)` | Получить данные из основного хранилища |

В обновлённом шаблоне оценка кешируется на **60 минут**, а интересы читаются по ключу `i:<cid>` и декодируются из JSON.

### Устойчивость к сбоям

- При разрыве соединения хранилище должно пытаться переподключиться **N раз**, прежде чем сдаться.
- Запросы не должны зависать: использовать **таймауты**, где это возможно.
- Исчерпание попыток обрабатывать с учётом различий между кешем и основным хранилищем.

### Различие требований к данным

В реальной системе кеш и основное key-value хранилище - отдельные источники. В рамках ДЗ допустимо использовать одно физическое хранилище для обоих назначений, но различие требований необходимо сохранить и проверить.

| Функция | Роль хранилища | Поведение при недоступности |
| --- | --- | --- |
| `get_score` | Кеш вычисленной оценки | Продолжает работать и вычисляет результат без кеша |
| `get_interests` | Основное хранилище интересов | Возвращает ошибку: достоверные данные получить невозможно |

> Ошибка доступа и отсутствие ключа - разные ситуации. В приложенном шаблоне отсутствие интересов даёт пустой список; недоступность основного хранилища не должна маскироваться под отсутствие данных.
